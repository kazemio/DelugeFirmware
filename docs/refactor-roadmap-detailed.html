Deluge Community Firmware Refactor Roadmap

Detailed edition. Forty-five behavior-preserving pull requests that take the Deluge firmware from invariants held in folklore to invariants held in types — with specifics drawn from the code as it exists today. The instrument never changes. The code beneath it does.

The vision

Same machine code. Different codebase.

The hardware dictates the mechanisms — cooperative scheduling, a stealable sample cache, static allocation. It does not dictate the structure. The end state runs identically on the same chip, but the source gains four properties it lacks today.

  1. One concurrency boundary

    Audio renders at interrupt priority and never blocks. Control code is plain single-threaded logic. The two communicate only through lock-free queues. The current scheme — the audio routine re-entered from inside SD-card waits, across roughly 400 call sites — disappears.

  2. Enforced cache ownership

    The stealable sample cache stays; it is what makes the instrument good. But holding sample data now means holding an RAII pin, so use-after-steal becomes impossible to write rather than hard to find.

  3. A model that runs anywhere

    Songs, clips, notes, automation, and undo compile and run on a laptop with no hardware headers. Today 43 of 183 model files include GUI or hardware code.

  4. Storage that never waits

    No code synchronously blocks on the SD card. Every wait removed deletes a place where the world could change underfoot.

A note on the toolbox

The codebase is further along than it looks.

Modern C++ is already established here: the firmware compiles with exceptions enabled and RTTI off, uses std::expected, and util/containers.h aliases standard containers over custom allocators (deluge::vector backed by memory::external_allocator into SDRAM, fast_allocator into on-chip RAM, both routing through the GeneralMemoryAllocator). memory/allocate_unique.h already returns std::unique_ptr with a custom deleter wrapped in std::expected. Every RAII and container technique this roadmap proposes has existing precedent in the tree — nothing here introduces a new idiom.

The rule

Shippable after every PR.

The device is fully functional after each individual pull request — buildable, flashable, behaviorally identical for users. There is never a broken window. New mechanisms are added alongside old ones; call sites migrate one PR at a time; the old mechanism is deleted only when its last user is gone. The two large changes (PRs 41 and 43–44) ship dark behind a build flag.

One mechanical transformation per PR, never bundled with an improvement. Each PR is either mechanically equivalent or verified by a golden master built before the change. Ratchet PRs — 15, 30, 36, 42 — make each retired pattern impossible to reintroduce.

Phases 0–2 can proceed in parallel. Phase 5 depends on 2 and 3; phase 6 depends on 4 and 5.

Phase 0 · PRs 1–5

Build the net first.

Past refactors failed because it was difficult to prove behavior preservation. These five PRs change no production code.

01Host build for the serialization stack

Compile the Serializer and Deserializer in the existing host test build, with an in-memory stand-in for the SD card.

First crack in the nothing-runs-off-device wall, proven on the friendliest subsystem.

storage/storage_manager.h defines abstract Serializer/Deserializer with XMLSerializer and JsonSerializer implementations built on a FileWriter base. The work is a new CMake target alongside tests/unit (CppUTest, with an existing mocks/ directory and tests/tracking_allocator.h) that compiles these classes with FileWriter's FatFS calls satisfied by an in-memory buffer.

02Golden-master song round-trips

Load a corpus of real songs, write them back, diff the output.

The cheapest regression net there is — any refactor that changes persisted state fails CI instead of corrupting a song.

The entry points are Song::readFromFile(Deserializer&) and Song::writeToFile() (model/song/song.h). Honest caveat: instantiating a full Song on the host requires phase 3 decoupling, so this starts smaller — round-tripping leaf objects whose serialization is self-contained (param/automation data, instrument settings), with full-song round-trips first running under QEMU and moving to the host as phase 3 progresses.

03Sequencer replay harness

Drive playback with a fake clock and record the emitted note and CC streams as golden files.

Catches what byte-diffs cannot: a refactor that moves a note by one tick.

PlaybackHandler (playback/playback_handler.h) with Session/Arrangement in playback/mode/ drive event emission. Same caveat as PR 2: this code reaches the currentSong global graph (extern Song* currentSong, song.h), so the harness likely starts as a QEMU spec with a scripted clock and migrates to the host after phase 3.

04QEMU input scripts

Scripted button and pad presses with assertions on display and LED state, built on the community emulator effort rather than from scratch.

The only net that covers UI-layer refactors, which phases 4 and 5 lean on heavily — and the emulator work makes it far cheaper to build.

tests/qemu/ exists but currently runs a single CppUTest spec (fixedpoint_spec.cpp) under emulation. Input on real hardware arrives via the PIC coprocessor (drivers/pic, readButtonsAndPads() in extern.h); the emulator's device model is the natural place for an injection hook, with assertions against the OLED/7-segment display buffers.

05Debug assertions

An assert macro that freezes with a code on hardware, aborts on host, and compiles out of release builds — plus a re-entrancy depth counter.

Turns mysterious corruption later into a clear failure at the violation site.

The pattern already exists ad hoc: invariant checks guarded by #if ALPHA_OR_BETA_VERSION calling display->freezeWithError("E…") (virtual on Display, hid/display/display.h). This PR names it — one DELUGE_ASSERT macro — and adds a depth counter alongside the existing sdRoutineLock flag (extern.h) asserting the card routine is never re-entered.

Phase 1 · PRs 6–8

Make the invariants visible.

You cannot safely refactor across invariants you cannot see. Tooling only.

06Yield-point map

A script that computes every function that may indirectly run the audio routine mid-call, checked in as a report.

The invisible invariant behind the heisenbugs becomes a diffable document — and the progress metric for phase 5.

The roots are routineForSD() (declared deluge.h:39) and AudioEngine::routineWithClusterLoading() (processing/engines/audio_engine.h). The build already produces compile_commands.json via the dbt wrapper, so a clang-based script can walk callers transitively. Honest limit: virtual dispatch and function pointers make the map conservative and incomplete — it is documentation with teeth, not a proof.

07Yield-map diff in CI

Regenerate the map on every PR and surface changes to reviewers.

Stops new hazards from entering silently while old ones are drained.

A CI job that reruns the PR 6 script against the PR's compile database and posts added/removed functions as an informational comment. No gating — the map's incompleteness makes it advisory by design.

08Yield annotations

Generated doc comments on every function in the map.

Puts the danger at the call site, where decisions are made — not in a report nobody opens.

Mechanical insertion of a /// @yields-to-audio tag on the map's member functions, regenerated by the same script so it cannot drift from the report.

Phase 2 · PRs 9–16

Pin the sample cache.

About seventy manual refcount call sites become compiler-enforced ownership — the most bugs retired per line available anywhere in the codebase.

09Introduce ClusterPin

A move-only RAII handle whose constructor and destructor call the existing refcount functions verbatim. No call sites converted yet.

Identical behavior by construction; establishes the vocabulary every conversion uses.

The current API is asymmetric: acquire is Cluster::addReason() (storage/cluster/cluster.h, bumping numReasonsToBeLoaded), but release is AudioFileManager::removeReasonFromCluster(Cluster&, char const* errorCode, …) (storage/audio/audio_file_manager.h) because release may re-queue the cluster for deletion. The pin wraps exactly that pair, carrying the error-code string the release path already takes. Idiom precedent: memory/allocate_unique.h's unique_ptr-with-custom-deleter.

10Convert cluster.cpp and audio_file.cpp

Start at the mechanism's home, with the smallest blast radius.

These two files (plus cluster.h/audio_file.h) hold the reason calls closest to the allocator — including the cluster-creation path, where Cluster::create() takes a shouldAddReasons flag that becomes "returns a pin."

11Convert audio_file_manager.cpp

The largest cluster-juggling file; the most leak opportunities retired in one review.

The manager owns the loading pipeline — loadAnyEnqueuedClusters() and the ClusterPriorityQueue loadingQueue — where reasons are added when clusters are enqueued and removed on load completion or error. Each enqueue/dequeue pairing becomes a pin with explicit ownership transfer.

12Convert audio_file_holder.cpp and wave_table.cpp

Clears the remaining storage-side holders so only GUI and playback sites remain.

Holders keep clusters alive for loaded instruments; wavetables pin their source clusters during conversion. Both are straightforward member-variable conversions: a raw Cluster* plus manual reason becomes a ClusterPin member.

13Convert the sample browser and waveform renderer

GUI-side holders are where pins outlive UI state changes — historically fertile ground for leaks.

gui/ui/browser/sample_browser.cpp pins clusters for audition previews; gui/waveform/waveform_renderer.cpp pins them while drawing. Both interleave with SD loading and UI navigation, so the RAII conversion also documents exactly when preview data may vanish.

14Convert the playback path

The low-level sample reader and voice unassignment.

The sites where a stale cluster pointer means audible corruption under load.

model/sample/sample_low_level_reader.cpp holds reasons on the clusters a playing voice is reading and the ones queued ahead of it; voice unassignment in model/voice/voice.cpp releases them. These are the hottest sites — the conversion must preserve the exact release ordering, which the goldens and PR 16's detector check.

15Privatize the raw refcountRatchet

The compiler now enforces the invariant forever; manual refcounting cannot return.

Make Cluster::addReason() and AudioFileManager::removeReasonFromCluster() private with ClusterPin as friend. One special case to resolve: Cluster tracks numReasonsHeldBySampleRecorder separately for recording — it either gets its own pin type or stays an explicit documented exception.

16Pin-leak detector

Debug-build assert that reason counts match outstanding pins at destruction or steal.

Any conversion mistake surfaces at the violation site, before users find it.

A debug-only pin counter on Cluster compared against numReasonsToBeLoaded inside Cluster::steal() and destroy(), using the PR 5 assert macro. Zero release-build cost.

Phase 3 · PRs 17–30

Free the model from the hardware.

Forty-three model files include GUI or hardware headers. Each PR cuts a cluster of them loose; the count of host-compilable files only goes up, and the golden masters prove nothing changed.

17A reportFatalError() function

Replaces direct display-freeze calls throughout the model; the hardware build delegates to the display as before.

Removes the single most common reason model files include hardware headers.

Sixteen model/ files call through the display global today. A free function in a new model-safe header delegates to display->freezeWithError() on hardware and aborts on host. Pure delegation — same string codes, same freeze behavior.

18A narrow UI-notification interface

The model's tell-the-UI calls go through a small interface; hardware forwards to today's globals, the host records calls for tests.

Severs the model-to-GUI direction once, so the next eleven PRs become mostly include deletions.

Model files currently include view headers to invalidate rendering and post popups. The interface starts minimal — rendering-dirty, popup, numeric flash — and grows only as conversions demand. The host implementation records calls, which doubles as a test assertion point for "this edit marked the right rows dirty."

19Cut display.h from model_stack.h

The highest-fan-out include in the model; one deletion uncouples every ModelStack user.

model/model_stack.h includes hid/display/display.h for its inline error checks. After PR 17 those route through reportFatalError(), and the include — inherited by the 206 files using ModelStacks — disappears.

20Split runtime feature settings

Storage and lookup stay in the model; the menu moves to the GUI.

Flags are read everywhere; the split lets host tests exercise flag-dependent model behavior.

RuntimeFeatureSettings (model/settings/runtime_feature_settings.h) mixes the settings table with menu-facing strings and includes GUI headers. The lookup side (get()-style reads) stays; menu construction moves next to the menus that use it.

21Move the clip minders to gui/

A pure file move, no edits.

They are UI logic misfiled in the model; relocating them shrinks the work without touching a line.

model/clip/clip_minder.cpp and instrument_clip_minder.cpp/h handle button presses and view transitions — UI dispatch that lives in model/ for historical reasons. Moving them removes four files from the decoupling count for free.

22Decouple notes

Note rows hold the most test-worthy logic in the firmware — quantize, nudge, MPE.

model/note/note_row.cpp/h (~4,500 lines). Its GUI includes serve rendering invalidation and error display — both covered by PRs 17–18, so this is largely include surgery plus relocating any drawing helpers that turn out to live here.

23Decouple clips, part one

The clip base class, audio clips, and clip instances.

Clears the base layer so the hardest file becomes an isolated effort.

model/clip/clip.cpp/h, audio_clip.cpp/h, clip_instance.h. The base Clip carries UI state (view positions, colors) that stays — it's data, not a dependency; only the calls into view code route through the PR 18 interface.

24Decouple clips, part two

instrument_clip.cpp — 4,700 lines, the worst file in the phase.

Once host-compilable, the replay harness covers real clip logic.

The single largest model file with GUI includes. Expect this to surface the genuine two-way couplings — places where model methods make view-mode decisions — which is exactly the design work the priorities section warns about. Budget accordingly.

25Decouple the song

The 6,100-line centerpiece becomes host-testable; round-trip tests now exercise the true load and save path.

model/song/song.cpp/h. After this lands, PR 2's golden masters upgrade from leaf objects to full Song::readFromFile()/writeToFile() round-trips on the host, and PR 3's replay harness can begin migrating off QEMU.

26Decouple instruments

Kits, melodic and MIDI instruments, drums, outputs.

Brings MIDI and CV behavior under host test — where community features concentrate.

model/instrument/kit.cpp, melodic_instrument.cpp, midi_instrument.cpp, model/drum/*, output.h. MIDI-follow and similar community features route through these files; host tests here have immediate payoff for active development.

27Decouple samples

Holders, the low-level reader, the recorder.

A prerequisite for phase 5: code being made asynchronous must be testable first.

model/sample/sample_holder.cpp, sample_low_level_reader.cpp, sample_recorder.cpp. The reader is the consumer side of the cluster pipeline PR 41 later rewrites — its host tests (with fake clusters) are the safety net that conversion runs under.

28Decouple undo

The consequence system and action logger.

Undo bugs are catastrophic and currently untestable; do–undo round-trips become host tests.

model/action/action_logger.cpp/h and model/consequence/* — several consequence types include view headers to refresh the UI on revert; those calls route through PR 18. Host tests then assert that every Consequence type's revert restores byte-identical serialized state.

29Decouple the remainder

Mod-controllables, global effects, voices, sync.

Completes the sweep so the gate can defend the whole territory.

model/mod_controllable/ (including mod_controllable_audio.cpp), model/global_effectable/, model/voice/voice.cpp, model/sync.cpp, plus stragglers like model/action leftovers. The long tail — each small, none structurally novel after PRs 17–18.

30CI gate on the modelRatchet

The count of host-compilable model files may never decrease.

Turns the phase's outcome from a current state into a permanent property.

A host CMake target that compiles model/ sources directly (no mocks), with a checked-in list of conforming files. CI fails if a file regresses off the list; adding files is the only allowed direction.

Phase 4 · PRs 31–36

One way to defer.

There are 169 hand-rolled instances of "do this outside the card routine." Funnel them through one tested queue, so the endgame has a single choke point instead of 169.

31Introduce a deferred-actions queue

Bounded callbacks drained from the main loop, unit-tested on the host.

One tested mechanism replaces 169 hand-rolled copies of the same idea.

Deliberately not a deluge::vector of std::function — that heap-allocates through the GeneralMemoryAllocator at exactly the boundary where allocation is unwelcome. Instead: a fixed-capacity ring of small POD command structs, drained from the main loop in deluge.cpp. Statically allocated, no exceptions on the enqueue path.

32Convert the session and arranger views

The most timing-sensitive deferral users; proving the queue under the hardest load first.

Sites returning ActionResult::REMIND_ME_OUTSIDE_CARD_ROUTINE (definitions_cxx.hpp) in gui/views/session_view.cpp (4,900 lines) and arranger_view.cpp (3,400). Each conversion swaps "return the sentinel and get re-dispatched later" for "enqueue the action now" — same execution timing, explicit instead of implicit.

33Convert the clip and automation views

The two largest view files; the bulk of remaining sites.

gui/views/instrument_clip_view.cpp (7,900 lines, the largest file in the firmware) and automation_view.cpp (3,300). Mechanical repetition of the PR 32 pattern.

34Convert browsers, menus, load and save

These sites interleave with SD access — exactly where deferral mistakes corrupt state today.

The browser stack (gui/ui/browser/, including sample_browser.cpp), sound_editor.cpp, and the load/save UI flows — the deferral sites that fire while the card routine is most active.

35Convert the global handlers

Buttons, mod wheel, MIDI learn.

Sweeps the long tail so the pattern can be deleted.

Remaining sites in gui/views/view.cpp (the shared mod-encoder and learn handling) and scattered single-site files found by grepping the sentinel.

36Delete the old patternRatchet

Remove the sentinel and its plumbing.

The ad-hoc pattern becomes unexpressible; all deferred mutation flows through one auditable funnel.

Delete REMIND_ME_OUTSIDE_CARD_ROUTINE from the ActionResult enum and the re-dispatch logic in the button/pad handling that services it, along with the allowSomeUserActionsEvenWhenInCardRoutine escape hatch (extern.h) if its last users converted cleanly.

Phase 5 · PRs 37–42

Stop waiting on the card.

Every synchronous SD wait is a place where the world can change underfoot. Convert leaf-first; the yield map shrinking to zero is the acceptance proof.

37Async SD request API

Issue, poll, complete — added alongside the synchronous path, with no callers yet.

Additive and risk-free; establishes the pattern every conversion follows.

Built above the SD driver (drivers/sd/sd.c and the RZ/A1 SDHI layer beneath it) and the FatFS port. Precedent already in the tree: cluster loading is already queued asynchronously via ClusterPriorityQueue loadingQueue and loadAnyEnqueuedClusters() — this PR generalizes that shape to non-cluster reads.

38Convert sample preview

The lowest-stakes SD path — a mistake mis-previews a sample rather than corrupting playback. The right place to learn.

The audition path in gui/ui/browser/sample_browser.cpp, which currently loads metadata and first clusters with synchronous waits that crank the audio routine. Becomes a state machine: request, render "loading," complete.

39Convert waveform rendering

Removes yield points inside UI rendering, where re-entrancy is least expected.

gui/waveform/waveform_renderer.cpp reads sample clusters mid-draw. Conversion renders what is cached and requests the rest, redrawing on completion — the standard progressive-render pattern.

40Convert metadata reads

Browser columns and sample-length scans.

After this, only the streaming core still waits.

Directory listing and WAV-header reads in the browser stack and storage/audio/audio_file.cpp paths (file_item.h entries). Mostly latency-tolerant code already, so the state-machine conversion is low-drama.

41Convert the streaming prefetcherBuild-flagged

The sample-streaming core becomes fully event-driven; the old path stays default until soaked.

The big one — the core reason audio must be hand-cranked during waits. Gated on phases 2 and 3.

The pipeline is AudioFileManager::loadAnyEnqueuedClusters() feeding SampleLowLevelReader's cluster-advance, with routineWithClusterLoading() cranking audio during stalls. The conversion makes voice start and cluster-advance purely completion-driven (pins from phase 2 guarantee lifetime; host tests from PR 27 cover the reader). Ships behind a build flag with the synchronous path as default.

42Remove the yield callsRatchet

Delete routineForSD() from each converted subsystem.

The yield map shrinks toward empty; each removal permanently deletes a class of bugs.

Per-subsystem deletion of routineForSD() calls as conversions land, with the PR 6 map regenerated as proof. The map reaching empty is the formal precondition for phase 6.

Phase 6 · PRs 43–45

Invert the engine.

After phases 4 and 5, mutations are funneled and yield points are gone. Moving audio to interrupt priority becomes a small change to a prepared codebase, not a heart transplant.

43Audio from the DMA interruptBuild-flagged

Render at interrupt priority behind a build flag; main-loop cranking stays the default.

Proves the inversion empirically with zero risk to release users.

Audio output runs through the SSI peripheral fed by DMA (drivers/ssi, drivers/dmac); the flag moves the render call into the DMA buffer-completion interrupt. One constraint this codebase makes explicit: exceptions are enabled (fast_allocator throws deluge::exception on exhaustion), so the render path must be audited noexcept end to end — allocation-failure-by-exception stays a control-side idiom.

44The command queueBuild-flagged

A lock-free queue at the control–audio boundary; debug asserts verify no direct cross-boundary writes remain.

Establishes the single explicit boundary of the vision; control code becomes plain single-threaded logic.

A single-producer single-consumer ring using std::atomic (available; RTTI is off but atomics are not), statically allocated. The phase 4 deferral queue is the model: same POD-command shape, opposite direction. PR 5 asserts flag any remaining direct writes to render-side state from control code.

45Flip the default

After a community-beta soak, delete the legacy scheduling path.

Audio that cannot glitch on SD latency — and a concurrency story that fits in one paragraph.

Remove the main-loop render cranking and the last routineWithClusterLoading() machinery once the flag has soaked through a community beta. The deleted code is the ~400-site yield apparatus this roadmap set out to retire.

Priorities

Not all 45 carry equal weight.

An honest accounting: the value is unevenly distributed, and the scarce resource in a volunteer project is maintainer review, not authorship. The tiers below are how this roadmap should be read — the first tier is the actual proposal; the rest is direction.

  • Do first — phases 0 and 2. Thirteen PRs, high confidence. The verification net and cluster pins retire bugs the community actually hits — corrupted songs, reason-count freezes — are cheap to review, and stand alone. Roughly a fifth of the effort for most of the risk-adjusted value.
  • Do incrementally — phase 3. The biggest enabler in the plan, and heavier than it looks: perhaps a third of the 43 files hide real design decisions, not mechanical include-deletions. Pursue file by file, as review bandwidth allows.
  • Decide later — phases 4 through 6. Architecturally right and practically optional. "The inversion becomes small after phases 4 and 5" is a design thesis, not a demonstrated fact — and the current scheduling demonstrably ships. Commit only once the earlier tiers have proven out.
  • One known caveat. The sequencer replay harness (PR 3) likely depends on phase 3 decoupling to run on a laptop; it may need to start life in the QEMU emulator and move to the host later.

Verification

How each phase proves itself.

  • Phases 0–1. No production changes; the new harnesses and scripts simply run in CI.
  • Phase 2. Golden masters and the QEMU smoke test green on every PR; the leak detector validates conversions on hardware.
  • Phase 3. Byte-identical round-trips and identical event streams on every PR; the host-compilable file count only rises.
  • Phases 4–5. QEMU scripts cover UI behavior; the yield-map diff documents each shrink; debug builds assert through beta.
  • Phase 6. A/B builds on hardware, audio-output diffs under scripted load, and a community soak before the flip.

Outcome

The same instrument, on a codebase that can be changed with proof instead of courage.

Nothing about the Deluge itself changes — same sound, same workflow, same hardware. What changes is everything around it: the freeze and corruption bugs that came from stolen memory and re-entrant timing are structurally impossible rather than merely rare; the model runs and is tested on a laptop in milliseconds instead of flash-and-listen on hardware; audio cannot glitch on SD latency; and the concurrency story fits in one paragraph instead of in the heads of a few veterans. A contributor's change is proven safe by CI before it ships — which is the difference between a codebase the community maintains and one it merely survives.

Related work

Alongside the emulator.

A community QEMU-based Deluge emulator is already in progress, and this roadmap is designed to compound with it rather than duplicate it. The emulator answers how do I run the firmware without hardware; this work answers how do I prove a change is safe, and how do bug classes become impossible to write. The two meet in the middle: the emulator gives the roadmap a cheap home for scripted regression specs (PR 4) and a soak venue for the build-flagged changes in phases 5 and 6, while the roadmap gives the emulator something an emulator alone can never provide — millisecond unit tests that pinpoint the failing line, and structural guarantees that don't depend on reproducing timing. The one thing emulation cannot do is recreate real SD latency and memory pressure, which is where the heisenbugs live — so golden masters, the host-runnable model, and a final hardware soak remain essential even in a fully emulated world.

One practical step before phase 0 begins: coordinate with the emulator's authors. If their device model exposes a scripting hook for input injection and display readback, PR 4 shrinks to glue code.
